# GitHub release management

## Scope and version policy

`.github/workflows/create-release.yml` automatically creates a GitHub prerelease and an annotated `vMAJOR.MINOR.PATCH` tag after the `Validate website` push run succeeds for the current `master` commit. Automatic releases use a patch bump. It does not deploy the website. A manual dispatch from `master` remains available for recovery, requires `CREATE_RELEASE`, and lets the owner select patch, minor, or major.

The first baseline is `v0.1.0`; if no version tags exist, the first default patch release is `v0.1.1`. Choose one of `patch`, `minor`, or `major`:

- Patch increments the patch number, for compatible fixes.
- Minor increments the minor number and resets patch to zero, for backward-compatible additions.
- Major increments the major number and resets minor and patch to zero, for incompatible changes.

Tags must be exactly `vMAJOR.MINOR.PATCH`, with no leading zeroes, suffixes, or build metadata. Any malformed `v`-prefixed tag, duplicate tag entry, or conflicting version stops release calculation. Version numbers are calculated from the highest existing version tag and the explicit bump choice.

Releases are always marked prerelease while the site is in private development. A GitHub prerelease is still visible wherever the repository is public; the prerelease marker does not provide access control. Publication/indexing and Cloudflare deployment remain separate owner-authorized decisions.

## How the release policy is checked

The release scripts no longer need opaque SHA-256 entries in `.github/ci/check_policy.py`. The policy names the safeguards it checks: successful `master` validation, the exact validated commit, duplicate-tag rejection, annotated-tag verification, generated notes, and prerelease status. Its self-tests run the authorization script with allowed and refused event examples, and mutate workflow settings to confirm unsafe changes are rejected. If a safeguard changes, update the named check and its test so the reason is visible in code review.

The separate Cloudflare deployment script fingerprints remain in place; this change only replaces the release-specific fingerprints.

## Automatic release and manual recovery

After a successful `Validate website` completion, the release workflow accepts only a `push` run whose branch and workflow name are exactly `master` and `Validate website`. It uses that run's head SHA, confirms it is still the current `master` head, and independently verifies the latest completed `validate.yml` push run for that exact SHA succeeded. Failed runs, pull request runs, development pushes, and stale commits cannot publish a release. The automatic version bump is patch; the existing SemVer helper rejects malformed or conflicting tags.

Manual recovery remains available from **Actions → Create GitHub Release → Run workflow**. Select `master`, choose `patch`, `minor`, or `major`, type `CREATE_RELEASE`, and start the workflow. It is subject to the same exact-SHA successful-validation, ancestry, duplicate-release, tag, and publication checks.

For either path, the workflow checks out the full source history without persisting checkout credentials, rejects an existing versioned Release for the same commit, creates an annotated tag, verifies the tag target, publishes generated notes as a prerelease, and verifies the resulting Release metadata.

The repository's protected `master` branch and existing tag ruleset must remain enabled. Configure branch protection to require pull requests and the validation checks. Keep tag rules that prevent updates and deletion for `v*`; do not grant this workflow a bypass. Permissions are separated by job: authorization uses `contents:read`; source/version/CI preparation uses `contents:read` plus `actions:read`; tag creation and release publication use only `contents:write`. The release workflow currently treats successful `validate.yml` push CI on the exact master commit as the required CI signal. If branch protection adds other required checks, update and review the release gate before using it.

## Routine release and summary

After a development-to-master PR is merged, wait for the `Validate website` push run to pass. The release workflow then creates the next patch prerelease automatically. Review the run summary for the version, source commit SHA, release URL, and creation timestamp. Confirm GitHub generated release notes from merged pull requests.

Do not rerun on another ref or alter the tag to work around a failure. The release notes are generated by GitHub's `--generate-notes` mechanism.

## Tag protection and blocked tag creation

The workflow creates an annotated Git tag object through the GitHub API and then asks GitHub to create the `refs/tags/vX.Y.Z` reference. Repository rules remain authoritative. If a tag ruleset blocks the reference, the workflow stops before publishing a release and reports that protection was not changed. Do not replace the token with a personal access token or weaken the ruleset.

If repository policy intentionally requires an automated exception, use a dedicated GitHub App installed only on this repository, grant only `Contents: write` (plus any read access demonstrably required), store its private key as a narrowly scoped Actions secret, and configure the App as an explicit, reviewed bypass actor only for the required `v*` tag rule. Keep the bypass unavailable to ordinary users and document its owner. Until such an App and ruleset change are separately approved, create releases through the existing owner-controlled process.

## Failure recovery

- **Authorization, CI, ancestry, version, or duplicate check fails:** no tag or release is created. Correct the underlying issue and start a new manual run after review.
- **Tag creation is rejected:** the workflow stops before release publication. Preserve the ruleset and use the owner-controlled release process or an explicitly approved GitHub App design.
- **Tag exists but release publication fails:** the run reports a `PARTIAL RELEASE`, including the tag and source SHA. The workflow does not delete the tag. Inspect the GitHub tag and failure, then recover by publishing that existing tag with generated notes and the prerelease flag, for example:

  ```sh
  gh release create vX.Y.Z --verify-tag --generate-notes --prerelease --title vX.Y.Z
  ```

  Use the exact tag reported by the failed run; verify it points to the reported source SHA first. Do not create a second version tag for the same source commit.

## Separation from deployment

Creating a GitHub Release does not trigger a Cloudflare deployment. The Cloudflare workflow remains independently manual and protected by its own `master`, private-deployment confirmation, Access-readiness checks, and environment credentials. No release event, tag event, or publication event is added as a deployment trigger. Indexing, custom domains, DNS, sales activation, and public launch remain separate approvals.
